Replacing a job queue with Postgres

September 7, 2026

For two years we ran a hand-rolled job queue on top of Redis. It worked, mostly. It also had a retry bug that surfaced maybe once a month, and I never found it. Last weekend I replaced the whole thing with a Postgres table and one query.

The problem

Jobs would occasionally run twice. Not often enough to page anyone, often enough that we had idempotency checks scattered through every handler. The queue itself was about 600 lines: enqueue, lease, heartbeat, retry, dead-letter. Each piece was simple. The interactions were not.

The replacement

Postgres has had SELECT ... FOR UPDATE SKIP LOCKED since 9.5. A worker grabs the next row nobody else holds, does the work, and deletes the row in the same transaction. If the worker dies, the transaction rolls back and the row is available again.

DELETE FROM jobs
WHERE id = (
  SELECT id FROM jobs
  WHERE run_at <= now()
  ORDER BY run_at
  FOR UPDATE SKIP LOCKED
  LIMIT 1
)
RETURNING *;

That's the queue. No heartbeats, no leases, no separate service to keep alive.

What we lost

Throughput, on paper. Redis could enqueue faster. We were doing about 40 jobs a second and Postgres handles that without noticing. If you need ten thousand a second, this isn't for you. Most people don't.

What we gained

Jobs live in the same database as the data they operate on, so enqueueing a job is part of the same transaction as the write that caused it. That closed a whole class of bugs where the write committed and the enqueue didn't, or the other way around. And the retry bug is gone, because the code that had it is gone.
